# Codex Usage Bar 앱 설계

작성: 2026-09-16 · 원래 설계안. 현재 구현과 검증 결과는 [IMPLEMENTATION.md](IMPLEMENTATION.md)를 참조한다.

## 1. 목표와 범위

MacBook 메뉴 막대의 아이콘을 클릭해 Codex 계정 약 4개의 사용량, 리셋 시각과 상태를 확인한다. 계정 전환을 위해 매번 로그아웃할 필요 없이 모든 등록 계정을 조회한다. 사진의 서비스 탭을 **Codex 계정 탭**으로 바꾸고, 첫 탭에 **전체 계정 비교**를 둔다.

사용자가 확정한 요구사항은 Codex 전용, 여러 계정 지원, 상태 확인이다. 아래 UI, 갱신 주기, 플랫폼과 저장 방식은 이를 구현하기 위한 제안이다. 참고 문서의 운영 명령이나 다른 서비스 기능은 제품 요구사항으로 간주하지 않는다.

| 우선순위 | 기능 | 동작 |
| --- | --- | --- |
| MVP | 다중 계정 | 독립 로그인 4개 이상, 추가·이름 변경·재인증·제거·순서 변경 |
| MVP | 전체 화면 | 계정별 플랜, 5시간/주간 사용률, 리셋까지 남은 시간, 조회 상태 |
| MVP | 계정 상세 | 사용률/남은 비율, 기간별 미터, 정확한 리셋 날짜, 마지막 성공 조회 시각 |
| MVP | 전체 사용량 | 서버가 제공하는 누적 토큰과 일별 활동을 별도 표시; 미제공은 `제공되지 않음` |
| MVP | 상태 확인 | 인증 상태, 조회 상태, 한도 상태를 각각 표시 |
| MVP | 갱신 | 자동/수동 갱신, 절전·잠자기 복귀, 실패 계정만 독립 재시도 |
| MVP | Mac 사용성 | 메뉴 막대 상주, Dock 아이콘 없음, 설정 창, 로그인 시 실행 선택 |
| 후속 | 알림·기록 | 한도 임박/리셋 알림, 계정별 사용률 변화 기록 |
| 후속 | 서비스 상태 | OpenAI 상태 피드 조회와 장애 표시; MVP는 상태 페이지 링크 |
| 후속 | 추가 정보 | 제공되는 추가 모델 한도, 크레딧/리셋 크레딧 상세 |

자동 계정 교체, Codex 작업 실행, 리셋 크레딧 소비, 이메일 발송은 이 앱의 조회 기능에 포함하지 않는다. 구독료와 API 비용, 로컬 추정 비용을 같은 수치로 취급하지 않는다.

## 2. `전체`와 사용량의 의미

`전체` 탭은 모든 계정을 보여주는 개요이다. 각 계정의 한도와 플랜이 다를 수 있어 퍼센트를 합산하거나 평균 내서 전체 가용량으로 표시하지 않는다.

`누적 토큰`은 계정 상세에 있는 독립 지표이다. 5시간/주간 한도의 퍼센트와 단위가 다르므로 같은 미터에 넣지 않는다. 이 값은 서버가 반환한 활동 집계이며, 모든 과거 사용이나 청구 내역을 완전히 포함한다고 주장하지 않는다. 미제공·일부 기간·지연은 해당 표시 영역에서 설명한다. MVP는 계정 간 누적 토큰 총합을 만들지 않는다.

기본 미터는 **사용한 비율**이다. `32% 사용 · 68% 남음`처럼 뜻을 명시하고, 설정의 남은 비율 표시를 선택하면 모든 화면의 미터 의미를 함께 바꾼다.

## 3. 화면과 상호작용

### 메뉴 막대

아이콘 1개만 둔다. 기본은 Codex를 나타내는 단색 미터이며, 사용자가 고정한 대표 계정의 두 창 사용률을 반영한다. 선택적 숫자는 `5h 32% · W 61%`이다. 대표 계정은 메뉴에서 상세 조회 중인 계정과 별개로 고정한다. 대표 계정 미등록 상태에서는 중립 아이콘을 쓴다.

다른 계정의 재인증/조회 실패는 작은 경고 배지로 알린다. 배지는 팝오버에서 이유를 설명한다. 아이콘이나 색만으로 상태를 전달하지 않으며 VoiceOver 이름에도 계정·기간·상태를 넣는다.

### 팝오버: 전체

목표 너비 420pt, 높이는 가용 화면에 맞춰 최대 약 680pt. 4개 계정 카드가 기본 배율에서 비교 가능하도록 한다. 많아지면 본문만 스크롤하고 탭과 하단 동작은 유지한다.

```text
Codex                         [새로고침]
[전체] [개인] [연구] [업무] [보조]

4개 계정 · 정상 조회 3 · 재인증 1

개인                 Pro · 정상 조회  ›
5시간  [████░░░░░░] 32% 사용 · 2시간 18분 후
주간   [██████░░░░] 61% 사용 · 3일 4시간 후

연구                Plus · 정상 조회  ›
5시간 … / 주간 …
업무                 Pro · 한도 도달  ›
5시간 … / 주간 …
보조                 Plus · 재인증 필요 ›
마지막 성공 조회: 09:30 · 현재 값 확인 필요

[계정 추가] [계정 관리]
[OpenAI 상태 페이지]             [설정]
```

카드를 누르면 해당 상세 화면으로 이동한다. 원래 계정 순서는 갱신 중에도 유지한다. `조회 실패`는 서비스 장애나 한도 도달을 뜻하지 않는다.

### 팝오버: 계정 상세

계정 별칭, 이메일, 워크스페이스, 플랜과 조회 상태를 표시한다. 기본 2개 미터는 기간명, 사용률, 남은 비율, 리셋 카운트다운 및 절대 시각을 제공한다. 예: `9월 16일 22:10 KST`. 연도가 다른 날짜는 연도도 표시하고 시스템 시간대를 따른다.

실제 창 길이를 확인해 300분이면 `5시간`, 10,080분이면 `주간`으로 표시한다. 다른 길이는 `15분`, `24시간` 등 실제 기간을 쓴다. `primary`를 무조건 5시간으로 해석하지 않는다.

누적 토큰/일별 활동은 아래 별도 영역에 둔다. 이 조회가 실패해도 정상적으로 읽은 한도 미터는 계속 표시한다. 추가 한도는 후속 버전에서 접이식 영역에 노출할 수 있도록 모델에 보존한다.

### 계정 추가·재인증

1. `계정 추가` → 별칭 입력 → 앱 전용 계정 저장소 생성.
2. `ChatGPT로 로그인` → 공식 로그인 URL을 기본 브라우저에서 연다.
3. 브라우저에 남아 있는 다른 계정 세션을 사용할 수 있으므로 완료 후 **확인된 이메일·플랜**을 보여주고 등록을 확정한다.
4. 이미 등록된 동일 주체/워크스페이스는 새 행 대신 기존 계정을 안내한다. 이메일은 표시 정보이고 계정 키로 쓰지 않는다.
5. 첫 조회 성공까지 `연결 확인 중`으로 표시한다. 로그인 성공만으로 사용량 조회 성공을 선언하지 않는다.

로그인은 한 번에 하나만 진행해 브라우저 콜백 충돌을 피한다. 취소·실패한 임시 저장소는 소유권을 확인해 정리한다. 재인증은 기존 계정을 바로 덮어쓰기보다 임시 홈에서 로그인하고 동일 주체인지 검증한 뒤 연결을 교체한다. 다른 계정으로 로그인한 경우 교체를 중단하고 별도 등록을 안내한다.

워크스페이스가 여러 개일 때 MVP는 로그인 결과의 워크스페이스에 고정한다. 공식 수단으로 특정 워크스페이스를 강제할 수 있는지 호환성 단계에서 확인한다. 별도 워크스페이스 선택 UI는 후속 범위이며, 확인하지 못한 식별자를 임의로 변경하지 않는다.

### 설정

계정 관리(별칭·정렬·대표 계정·재인증·제거), 갱신 주기(수동/1/2/5/15분, 기본 5분), 사용/남은 비율, 이메일 가리기, 로그인 시 실행을 제공한다. 제거는 앱이 소유한 해당 계정 홈·메타데이터·캐시만 삭제한다.

## 4. 사용량 조회: 공식 App Server 우선

[OpenAI 공식 App Server 문서](https://learn.chatgpt.com/docs/app-server)는 로그인, 계정 조회, 한도 조회와 토큰 활동 조회를 설명한다. 계정별 전용 `CODEX_HOME`에 연결한 자식 프로세스와 stdio RPC를 사용한다.

```text
계정 컨텍스트 생성 → codex app-server 실행
initialize → initialized
account/read → 주체 및 인증 유형 확인
account/rateLimits/read → 필수 한도 조회
account/usage/read → 지원 시 선택적 활동 조회
종료 및 파이프 정리
```

주요 서버 필드는 `usedPercent`, `windowDurationMins`, Unix 초 단위 `resetsAt`이다. `rateLimitsByLimitId`가 있으면 이를 우선하고 레거시 `rateLimits`로 호환한다. 활동 집계나 추가 크레딧의 null은 0으로 바꾸지 않는다. ChatGPT 로그인으로 연결하며 API 키 계정은 이 제품의 구독 한도 등록 방식으로 받지 않는다. 출처: [공식 App Server](https://learn.chatgpt.com/docs/app-server).

참고 앱은 직접 OAuth HTTP 조회를 기본으로 사용하고 RPC도 구현한다. `chatgpt.com/backend-api/wham/usage`는 참고 코드에서 확인했지만 여기서 공개 외부 API로 보장된 계약을 확인한 것은 아니다. 이 프로젝트의 MVP는 직접 HTTP나 WebView 스크래핑 없이 RPC부터 구현한다. RPC가 내부적으로 같은 서비스에 의존할 수 있어 서버 접근 제한을 우회하는 수단으로 보지 않는다.

Codex CLI는 사용자 설치 실행 파일을 우선 사용한다. 설정에 발견된 실행 파일 경로·버전을 표시하며 셸 명령 문자열 대신 `Process`의 실행 파일과 인자 배열을 쓴다. CLI가 없으면 설치 안내와 경로 지정 기능을 제공한다. 초기 배포에서 CLI를 함께 번들링하지 않는다.

단순 한도 조회를 위해 쓰기 작업이나 모델 응답을 실행하지 않는다. 프로세스는 앱 전용 빈 작업 디렉터리를 사용하고 불필요한 플러그인/MCP 등 시작 기능이 로드되지 않도록 설치된 버전의 옵션을 검증한다.

## 5. 계정 격리와 인증 저장

앱 전용 루트(제안):

```text
~/Library/Application Support/CodexUsageBar/
  accounts.json             # 별칭, UUID, 정렬, 검증된 주체 정보
  accounts/<UUID>/           # 개별 CODEX_HOME
    config.toml
    auth.json               # file 모드일 때 CLI가 관리하는 자격증명
  snapshots/<UUID>.json      # 토큰 없는 최근 성공 사용량
```

[공식 인증 문서](https://learn.chatgpt.com/docs/auth)는 `file` 모드의 홈별 `auth.json`과 OS 자격증명 저장소를 설명한다. MVP 제안은 **홈별 격리가 명확한 file 모드**이며, CLI가 토큰 생성·갱신을 소유한다. 파일 기반이라는 보안 특성을 계정 추가 설명에 알린다. 관리 정책이 이를 금지하면 강제로 우회하지 않고 등록 불가 이유를 표시한다.

홈과 인증 파일은 각각 0700/0600 권한을 보장하고 생성·갱신 후 검증한다. 인증 데이터는 로그, 목업, 분석 정보와 스냅샷에 저장하지 않는다. Keychain 전환은 홈별 계정 격리·삭제·백그라운드 접근을 실제 지원 버전에서 확인한 뒤 별도 결정한다. 확인 없이 보안 저장소를 두 개로 복제하지 않는다.

사용자 기본 `~/.codex`의 로그인과 이 앱의 4개 계정은 분리한다. 앱은 기본 인증 파일을 교체하지 않으며 기본 브라우저 쿠키나 Codex 데스크톱 세션을 자동 수집하지 않는다. 자식 프로세스의 환경 딕셔너리에만 지정 홈을 넣고 전역 셸 환경은 변경하지 않는다. 인증 관련 상속 환경이 계정 홈을 덮어쓰지 않도록 필요한 환경만 전달한다.

계정 식별은 앱 UUID + 검증된 로그인 주체 + 워크스페이스 식별자로 관리한다. 설치 버전의 `account/read`가 이메일·플랜만 반환하면, CLI 소유 인증 정보에서 최소 식별 정보만 읽는 어댑터를 검증해야 한다. 식별자를 얻지 못한 상태에서 이메일만으로 중복 제거하거나 재인증 교체를 확정하지 않는다. 토큰 내용이나 인증 파일 원문은 진단에 출력하지 않는다.

## 6. 앱 구조와 데이터 모델

제안 플랫폼은 macOS 14+, Apple Silicon 우선이며 Intel 지원은 빌드 환경 확보 후 확인한다. Swift 6, SwiftUI + Observation, AppKit `NSStatusItem`/`NSPopover`를 사용한다. 설정은 SwiftUI 창, 로그인 시 실행은 `SMAppService`로 구현한다. 외부 UI 프레임워크나 서버 없이 시작한다. 코드 서명·공증된 `.app` 배포를 목표로 한다.

```text
MenuBarController → PopoverView / SettingsView
                         ↓
                 AppModel (@MainActor)
                         ↓
RefreshCoordinator (actor) → AccountSession (계정별 actor)
                         ↓           ↓
                   SnapshotStore   CodexRPCClient → codex app-server
                         ↑
AccountRepository ← LoginCoordinator
```

| 모듈 | 책임 |
| --- | --- |
| App/UI | 메뉴 막대, 전체 카드, 계정 상세, 설정, 접근성 |
| AccountRepository | 비밀 없는 메타데이터, UUID·워크스페이스·홈 소유권 |
| LoginCoordinator | 순차 로그인, 임시 홈, 검증 후 계정 등록/교체 |
| AccountSession | 한 계정의 로그인/갱신/조회가 겹치지 않도록 직렬화 |
| CodexRPCClient | 프로세스, RPC 요청 ID, 초기화, 알림, 응답, 타임아웃 |
| RefreshCoordinator | 갱신 예약, 최대 2계정 동시 조회, 취소, 결과 검증 |
| SnapshotStore | 최근 성공 값, 스키마 버전, 원자적 저장·삭제 |
| Clock/Transport | 시간·프로세스 교체로 재현 가능한 검증 |

```swift
struct AccountContext: Sendable {
    let localID: UUID
    let verifiedSubjectID: String
    let workspaceID: String?
    let credentialGeneration: Int
    let homeURL: URL
}

struct QuotaWindow: Codable, Sendable {
    let bucketID: String
    let kind: WindowKind              // primary / secondary
    let usedPercent: Double?
    let durationMinutes: Int?
    let resetsAt: Date?
}

struct UsageSnapshot: Codable, Sendable {
    let accountID: UUID
    let subjectID: String
    let workspaceID: String?
    let credentialGeneration: Int
    let windows: [QuotaWindow]
    let fetchedAt: Date
}
```

위 코드는 계약 설명용이며 컴파일 가능한 구현은 아니다. 계정 활동은 별도 `ActivitySnapshot`에 누적 토큰, 날짜별 토큰, 조회 시각, 제공 범위를 저장한다. 인증/조회/한도 상태도 서로 독립된 필드로 관리한다.

창 식별 키는 `bucketID + kind`이다. 캐시는 주체·워크스페이스·인증 세대까지 검증한다. 계정 삭제·재인증·워크스페이스 변경·새 갱신 후 늦게 도착한 응답은 게시하지 않는다. 이메일과 플랜 변경만으로 다른 계정의 캐시를 가져오지 않는다.

## 7. 상태·오류·갱신 규칙

| 상태 | 사용자 표시 | 데이터 처리 |
| --- | --- | --- |
| 최초 조회 중 | 연결 확인 중 | 값 없는 로딩 상태; 0%로 표시하지 않음 |
| 성공 | 정상 조회 · 마지막 성공 시각 | 해당 계정만 갱신 |
| 한도 도달 | 한도 도달 · 적용 기간 | 조회 성공과 별도로 표시; 크레딧에 따른 실제 이용 가능 여부는 단정하지 않음 |
| 인증 갱신 실패 | 재인증 필요 | 해당 계정의 자동 반복 중단, 재인증 동작 제공 |
| 네트워크/타임아웃 | 조회 실패 · 이전 값 | 최근 성공 값 유지 + 오래된 값 표시 |
| CLI 미설치 | Codex CLI 필요 | 계정 사용률과 분리된 설치 안내 |
| 메서드 미지원 | CLI 업데이트 필요 | 한도 메서드는 등록 차단; 활동 메서드는 선택 지표만 미제공 |
| 식별 불일치 | 계정 연결 확인 필요 | 응답 폐기, 캐시 다른 계정에 연결 금지 |
| 날짜 경과 | 리셋 확인 중 | 카운트다운을 0에 고정하고 조회; 로컬에서 사용률 0%로 만들지 않음 |
| null/형식 오류 | 제공되지 않음 / 데이터 확인 필요 | 창별 검증; 유효한 다른 창은 보존 |

자동 갱신 기본 5분, 팝오버를 열면 60초보다 오래된 값을 갱신한다. 같은 계정의 중복 요청은 합친다. 절전 중 갱신은 중단하고 깨어날 때 오래된 계정만 조회한다. 화면의 카운트다운은 로컬 계산으로 갱신하며 초 단위 API 폴링은 하지 않는다.

실패 재시도는 1→2→5→15분과 작은 jitter를 적용하고 인증 실패는 재인증 대기한다. 서버의 재시도 힌트가 있으면 우선한다. 초기화 10초, 필수 조회 10초, 계정 전체 조회 30초를 초기 예산으로 제안한다. 선택적 활동 조회는 필수 값 게시 이후 수행하고 계정 마감 시간을 연장하지 않는다.

취소/타임아웃/종료 시 stdin과 읽기 작업을 닫고 앱이 소유한 자식에만 종료 요청을 보낸다. 짧은 유예 뒤 살아 있는 자식만 강제 종료한다. stdout/stderr를 함께 비우고 메모리·행 길이에 상한을 둔다. raw stderr를 그대로 사용자 로그에 남기지 않는다.

절대 시각을 못 받은 경우 `리셋 시각 미제공`으로 표시한다. 오래된 데이터의 리셋 날짜가 지난 경우 `리셋 확인 중 · 이전 사용률`로 바꾼다. 리셋 전 비정상적 사용률 감소·갑작스러운 날짜 변경은 추가 조회로 확인하고, 확인 전에는 이전 신뢰 값과 `변경 확인 중`을 표시한다.

## 9. 구현 순서와 완료 기준

### 단계 0: 인증·조회 호환성 확인

설치 버전과 생성된 RPC 스키마로 기능을 확인한다. 두 테스트 계정의 독립 홈에 로그인하고 앱 재시작·토큰 갱신·로그아웃에서도 서로 영향이 없는지 검증한다. 이 단계는 실제 로그인 테스트를 수행할 때 진행하며 현재 설계 작업에서는 수행하지 않았다.

필수 통과 조건: 신뢰할 계정 식별 정보 확보, 한도 조회 지원, file 저장 정책 허용, 홈 격리, 기본 Codex 로그인 보존, 잠자기 복귀와 자식 종료. 활동 조회 지원 여부는 기능 플래그로 기록한다. 미지원 계정/버전에서 없는 수치를 생성하지 않는다. 기본 홈을 변경하는 로그인이나 계정 교차 결과가 발생하면 UI 개발 전에 해결한다.

### 단계 1: 네이티브 화면

SwiftPM 또는 Xcode 앱 타깃을 만들고 테스트 데이터로 메뉴 막대, 전체/상세, 설정, 계정 없음·오류 화면을 구현한다. 화면 구조는 함께 제공한 `menu-bar-mockup.html`로 검토한다. 목업은 웹 시안이며 AppKit의 실제 재질·앵커·키보드 포커스 검증을 대체하지 않는다.

### 단계 2: 계정과 실데이터

RPC, 계정 등록/재인증, 저장소, 자동 갱신과 stale 처리를 연결한다. 조회 성공 계정과 실패 계정을 동시에 표시하고 실제 4개 계정으로 검증한다. 필요한 핵심 로직은 가짜 전송·가짜 시계·임시 홈으로 자동 검사한다.

### 단계 3: 사용·배포 검증

새 `.app`에서 클릭·바깥 클릭·Esc·계정 추가의 브라우저 이동·설정 창 포커스·VoiceOver·다크/라이트·작은 화면·잠자기 복귀를 확인한다. 서명·공증·로그인 시 실행·업데이트 안내를 마무리한다. 자동 업데이트와 외부 업데이트 라이브러리는 초기 MVP의 필수 의존성으로 두지 않는다.

| 검사 | 완료 조건 |
| --- | --- |
| 4계정 독립 조회 | 기본 Codex 로그인 변경 없이 각 계정의 실제 값이 올바른 행에 표시 |
| 기간/값 해석 | 0, 100, null, 다른 창 길이, 다중 bucket, 초 단위 리셋 시각을 구분 |
| 부분 실패 | 계정 1개의 실패 또는 활동 조회 실패가 나머지 한도 값을 가리지 않음 |
| 겹친 요청 | 삭제·재인증·새 요청 이후 늦은 응답이 게시되지 않음 |
| 리셋 | 날짜 경과 시 확인 조회, 서버 응답 전 임의 0% 표시 없음 |
| 자격증명 | 인증 파일 권한, 소유 홈만 삭제, 비밀 출력 없음 |
| 프로세스 | hung child, stderr flood, 취소, 종료 후 자식/읽기 작업 잔존 없음 |
| UI | 4개 카드 비교, 키보드/VoiceOver, 실제 새 번들의 메뉴 막대 동작 |

성능 목표는 클릭 후 캐시 표시 200ms 이내, 네트워크 대기는 비동기이다. 상시 4개 App Server를 띄우지 않고 조회 중 최대 2개만 사용한다. 이는 설계 목표이며 실제 배터리·메모리·실행 시간 측정 결과는 아니다.

## 10. 현재 검증 범위

첨부 화면, 로컬 참고 코드와 공식 문서를 읽어 설계를 작성했다. 네이티브 앱·실계정 로그인·4계정 조회·인증 저장소 격리·배포는 아직 검증하지 않았다. 샘플 목업의 계정·플랜·사용량·날짜는 전부 가상 데이터이다.

브라우저에서 목업의 4계정 개요, 상세 사용률·리셋 날짜, 다크/라이트 화면, 남은 비율 표시, 이메일 가리기, 조회 실패 시 이전 값, 리셋 확인 중, 계정 없음과 추가 창을 확인했다. 다크 모드에서 일부 텍스트가 어둡게 상속되던 문제를 수정하고 화면을 다시 확인했다. 이 확인은 목업의 표시·상호작용 검사이며 실제 Codex 조회 검증은 아니다.
